## 0. 一句话结论

**顶栏 `rememberTitleBackdrop` 的内容录制层是最大的单一开销**：为了顶栏约 50dp 高的模糊条，
它每帧把整个页面内容（所有行）重录一遍。隔离它之后：FillRectOp **−34%**、重录图层 **−36%**、
`Drawing` **−16%**、137×137 采样层 **归零**。这是本轮找到的第一处"真冗余"，且修复方向不砍视觉。

## 2. 三个结论及其证据链

### ① 顶栏内容录制层 = 最大单一成本（钉死，含代码行）

- 代码：`Title.kt:345 rememberTitleBackdrop()` → `rememberLayerBackdrop(onDraw)`，
  `onDraw` 里 `drawRect(3×size)` + `drawContent()` —— **把整个页面内容录进 backdrop 层**。
- 使用点：`OnlinePlaylistDetail.kt:455`（以及所有用 `rememberTitleBackdrop` 的页面）。
- 消融 C（onDraw 改为不录内容，其他不动）：fills 191→127、重录层 11.3→7.2、Drawing 8.51→7.14ms、
  137×137 从 4/帧 → **0**。
- v1 里"137×137 的子节点是行内容"的现象正是采样层在录行。
- **为什么"关液态玻璃"没用**：`Title.kt:985` 两个分支（渐进模糊 / drawPlainBackdrop）**都**要采样
  同一个 backdrop，开关只换效果不换采样。这解释了消融 2 的零变化。

### ② 行级纹理每帧重传与顶栏采样无关（独立问题，未解）

- 消融 C 后行纹理重传仍是 6.0/帧（不变）。
- 即：滚动时每帧有 ~5-6 张 1190×140/189 的行级位图被重新光栅化上传，来源在行渲染自身，
  与顶栏、底栏、玻璃开关都无关。这是下一个要钉的对象。

### ③ ~190 fills/帧是"带 Title 的列表页"的通用量级（不是歌单页特有）

- 歌单 191 ≈ 设置页 196；首页（卡片流、无返回键 Title）只有 96。
- 结合消融 C：这 ~190 里有 ~64 来自顶栏采样，剩余 ~127 是页面自身内容 + 外壳的正常水平。

## 3. 修复方向（都不砍视觉，按性价比排）

1. **缩小顶栏采样的录制范围**：模糊只需要顶栏下方一小条（bar 高度 + blur 半径 + 淡出尾巴 40dp），
   现在 `onDraw` 录的是整页 3× 超采。把录制 clip 到条带区域，或对 backdrop 降采样（0.5x——模糊本身
   会掩盖精度损失）。预期直接拿回消融 C 显示的 −34% fills / −16% Drawing。
2. **只在 barVisible 时录制**：页面在顶部、顶栏背景未出现时（`barVisible=false`）不需要采样。
   需确认库层是否已做；从静止 0 帧看静止时无成本，主要是滚动全程都在录。
3. 行纹理重传（6/帧）单独立案：查行内容为何每帧失效（候选：LazyColumn item 状态写入、
   下拉刷新指示、行内锚点联动 `liquidDropdownAnchorFollow` 的每帧属性写入）。
4. 底栏玻璃容器（navplain 显示 −46 fills/帧）与顶栏采样是同库同机制（LayerBackdrop），
   修 1 时应一并检查底栏采样范围。
