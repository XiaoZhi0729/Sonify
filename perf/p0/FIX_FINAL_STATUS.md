## 2. 机制解释（按要求补，基于上一轮消融数据）

消融 ABBA 显示 `Drawing` 合计不变（8.90→8.95ms）但 miss3 −18.9pp。原因：
**每帧 ~250 个微秒级 op 的 onPrepare/onExecute 是 CPU 尖峰源**。按需录制把进入动画期间
的 op 数砍掉 21%（fills 184→147/帧）、saveLayer 砍 46%，
把**关键帧**的 UI 线程耗时从"跨过 3 个 vsync"压回到 2-3 个 vsync 边界内。
`Drawing` 是全部帧的合计——被削掉的帧省了，被测窗口里大量已达标帧没变化，所以合计不动；
miss3 是尾部统计，对尖峰敏感。**收益来自尖峰削减，不是绘制总时间下降。**

# 追记（2026-10-24 下午）：第四版（闭包修复版）结果与最终回退

## 发生了什么

用户第二次报告顶栏模糊消失后，我修好了验证仪器（顶栏结构判据：p95-p5，纯色=0、正常≈30），
据此完成：

1. **复现**：坏包顶栏 `p95-p5=0.0` vs 基线 `29.0`（判据成立）。
2. **读库定位**（decompile com.kyant.backdrop 1.0.5）：`LayerBackdropNode.draw()` 每帧无条件
   `recordLayer`，录制行为本身没有条件分支。
3. **埋点定位真根因**（YosDiagnostics 临时埋点，release 存活）：
   `onDispose { if (barVisible.value) demand-- }` 读的是**翻转后的当下值**——
   "从未 +1 的旧 effect" 执行了 −1，与新增 effect 的 +1 抵消，**demand 恒为 0**，
   生产者永远不挂。三版"模糊消失"全部由这一个闭包捕获 bug 造成。
   （`GlassProbe.prodemand` 的 shell 先例注释里"按需挂载可能首帧闪空"的风险描述与此吻合。）
4. **v4（闭包修复版）**：视觉全部通过——顶栏判据 `12.9/32.0` 与基线逐位一致。

## 但 v4 死在性能上，按纪律回退

单轮 ×3 复测（进入歌单，同协议）：

| 变体 | 帧数/2.5s | 帧跨度 | 帧率 |
|---|---|---|---|
| 基线 | 115–120 | 1815ms | **63fps** |
| v4 | 49–62 | 2782ms | **18fps** |

不是"提前完成"，是**入场帧率崩到三分之一**。判据侧 fills 139/帧（录制确实被抑制）、
miss3 反而更低（27–29 vs 35–38），但 miss2 76–95% vs 49–53%。生产者"条件挂载"这个动作本身
（LazyColumn 修饰符链结构变化 → 整列表重排，疑似 barVisible 边缘抖动放大）造成的代价
超过了省下的录制开销。

对比：**消融版（生产者常驻、onDraw 跳过内容）没有这个问题**——它才是拿到 −1.32ms/−18.9pp
的版本。条件挂载是我为规避"层失效"引入的第二机制，被证明有害。
